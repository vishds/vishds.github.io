Go unsafe string trick

I have a TCP server where I read AIS140 packets in ASCII format. There are floating point fields which have like Speed, Latitude, etc which I need to parse. strconv.ParseFloat requires a string and not a byte slice. Converting a byte slice to string will cause an allocation since the string type is immutable.

Each instance of this service handles thousands of packets per second. So it would be nice to avoid an allocation in the hotloop. I found the following trick to convert a byte slice to string without allocation using the unsafe package. 

tmp := unsafe.String(unsafe.SliceData(b), len(b))

I'll be only using this in production code after I benchmark and ensure it makes a difference. Also, the only risk I'm aware of is that the byte slice should not be modified during the lifetime of the string. This is ensured by design. So I hope I'm not introducing a bug here.

After a few days I figured out that the fasthttp package uses the exact same trick. I will be using that package as a reference for more related ideas.


Implementing my own CORS middleware

While implementing a REST API server at work, I had to implement my own CORS middleware. It was the first time I implemented one. My first iteration was as follows: 


func CORS(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        w.Header().Add("Access-Control-Allow-Credentials", "true")
        w.Header().Add(
            "Access-Control-Allow-Headers",
            "Content-Type, Content-Length, Accept-Encoding, Authorization, accept, origin, Cache-Control, X-Requested-With",
        )
        w.Header().Add("Access-Control-Allow-Methods", "POST, GET, PUT")
        next(w, r)
    }
}

I took a reference from a code example on the internet and copied only what made sense to me. I ran into my first issue, I did not allow OPTIONS method. Before the browser does a POST, it will do a preflight check with OPTIONS method to see whether the request is safe to send. This was being blocked. So I added OPTIONS to the allowed methods:

Looking up the MDN docs on CORS , I realised that the server also need to respond to these checks with 204 No Content. Hence I added: 


if r.Method == "OPTIONS" {
    w.WriteHeader(http.StatusNoContent)
    return
}

The docs also issued a warning in the context of Private APIs:

Warning: Using the wildcard to allow all sites to access a private API is a bad idea.
To allow any site to make CORS requests without using the * wildcard (for example, to enable credentials), your server must read the value of the request's Origin header and use that value to set Access-Control-Allow-Origin, and must also set a Vary: Origin header to indicate that some headers are being set dynamically depending on the origin.

So basically, I need to read the Origin header and set it to Access-Control-Allow-Origin. I also have to set the Vary header to indicate to the browser that it changes based on Origin and manage cache accordingly. 


origin := r.Header.Get("Origin")
if origin != "" {
    w.Header().Set("Access-Control-Allow-Origin", origin)
    w.Header().Set("Vary", "Origin")
} else {
    w.Header().Set("Access-Control-Allow-Origin", "*")
}

The final iteration:


func CORS(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        origin := r.Header.Get("Origin")
        if origin != "" {
            w.Header().Set("Access-Control-Allow-Origin", origin)
            w.Header().Set("Vary", "Origin")
        } else {
            w.Header().Set("Access-Control-Allow-Origin", "*")
        }
        w.Header().Add("Access-Control-Allow-Credentials", "true")
        w.Header().Add(
            "Access-Control-Allow-Headers",
            "Content-Type, Content-Length, Accept-Encoding, Authorization, accept, origin, Cache-Control, X-Requested-With",
        )
        w.Header().Add("Access-Control-Allow-Methods", "POST, OPTIONS, GET, PUT")
        if r.Method == "OPTIONS" {
            w.WriteHeader(http.StatusOK)
            return
        }
        next(w, r)
    }
}

Odin's defer differs from Go's defer

As per the Go Blog:

A defer statement pushes a function call onto a list. The list of saved calls is executed after the surrounding function returns.

Odin's defer implementation is what we (atleast I) expect to happen. Odin's Overview states:

A defer statement defers the execution of a statement until the end of the scope it is in.

While looking it up to add the hyperlink here, I realised that it directly says:

The defer construct in Odin differs from Go’s defer, which is function-exit and relies on a closure stack system.
